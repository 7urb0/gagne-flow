## 二、记忆系统加固（基于知乎文章《Agent记忆系统从踩坑到进化》）

### 文章洞察 → 本项目落地映射

| 文章痛点 | 项目原缺陷 | 落地改动 |
|:---------|:-----------|:---------|
| 坑二：记忆丢失（服务器迁移/扩容） | LTM 仅存 Redis（TTL 30 天），无 MySQL 兜底 | **P0**：LTM 事实 MySQL 持久化 + 降级重建 |
| 坑三：中间立场污染（存了中间讨论而非最终结论） | LTM 从摘要规则提取，无来源区分 | **P1**：事实来源阶段标注 + 检索加权 |
| 记忆随会话删除残留 | `/api/chat/clear` 不清理 LTM | **P0**：删除会话联动清理 Redis + MySQL |

### P0-1：LTM 事实 MySQL 持久化兜底

| 文件 | 操作 | 说明 |
|:-----|:----:|:-----|
| `entity/LtmFact.java` | 新建 | 实体：`factId`(业务主键=UUID)/`userId`/`sessionId`/`factText`/`factType`/`sourcePhase`/`createTime`；`ddl-auto: update` 自动建表 |
| `repository/LtmFactRepository.java` | 新建 | `findByUserIdAndSessionId` / `deleteByUserIdAndSessionId` |
| `service/memory/LongTermMemoryService.java` | 修改 | ① 构造器注入 `LtmFactRepository` ② `storeFacts()` 末尾 `saveAll` 双写 MySQL（失败不影响 Redis 主流程，仅告警）③ `searchFacts()` Redis 空时 `rebuildFromMySql()` 从 MySQL 恢复事实回 Redis 再检索 ④ `clearSessionFacts()` 联动 `deleteByUserIdAndSessionId` |

**验证**：`LongTermMemoryServiceExtendedTest` 新增 3 用例（saveAll 被调用 / MySQL 写失败容错 / 删除联动），全部通过。

### P0-2：删除会话联动清理 LTM

| 文件 | 改动 |
|:-----|:-----|
| `controller/SessionController.java` | `/api/chat/clear` 追加 `longTermMemoryService.clearSessionFacts(uid, sessionId)`（包 try-catch 不影响主流程） |

> **发现的真实缺陷**：原实现只删 MySQL `SessionMessage`，Redis `ltm:*` 与 MySQL `ltm_fact` 均残留，已删除会话的事实会被后续检索引用。

### P1：事实来源阶段标注（缓解"中间立场污染"）

| 文件 | 改动 |
|:-----|:-----|
| `LongTermMemoryService` | ① `MemoryFact` 新增 `sourcePhase`/`factType` 字段 ② 常量 `SOURCE_SUMMARY`/`SOURCE_USER`/`SOURCE_FINAL` ③ detail 存储格式升级为 `factText|sourcePhase`（兼容旧数据 `split("|",2)`）④ `vectorSearch()`/`keywordSearch()` 解析来源并按 `sourcePhaseWeight` 加权（`FINAL_DECISION`/`USER_EXPLICIT`=1.0，`SUMMARY_EXTRACTED`=0.85） |
| `ConversationMemoryManager.java` | `extractFactsFromSummary()` 两处创建 `MemoryFact` 时标注 `SOURCE_SUMMARY` + `factType=ss.category` |

**设计意图**：中间讨论（SUMMARY_EXTRACTED）权重 0.85 < 最终结论（1.0），后续接入教案回灌 `FINAL_DECISION` 时即可让最终决策排前，减少"暂不调整"类中间立场污染。

### 未实现（下个迭代）

- LTM 访问频率计数 + 认知权重（`accessCount`/`lastAccessTime`，排序 `cosine*0.6 + access*0.4`）
- 低价值事实自动衰减/合并（`@Scheduled` 凌晨，30 天未访问软删除）
- 关键词精确匹配索引（分词预计算，解决"退钱" vs "退款"）
- RL 训练记忆操作、图数据库——评估认为与应用层定位不匹配，不引入

## 四、启动测试暴露并修复的 3 个真实缺陷（真实环境验证）

环境：Docker MySQL/Redis/Milvus + `mvn spring-boot:run`，注入 `JWT_SECRET`/`DB_*` 环境变量 + `--spring.ai.mcp.client.enabled=false`。

| # | 缺陷 | 根因 | 修复文件 |
|:-:|:-----|:-----|:---------|
| 1 | Prompt 版本管理回归（v1 迁移引入） | `seedFile()` 传带 `.md` 路径给 `fileLoader.load()`（cache key 不带 .md）；`loadFallback()` 硬编码 `"addie/"` 前缀 | `PromptRegistry.java`：seed 传 key 去 `.md`；fallback 依次尝试 `v1/addie/`、`addie/`、`v1/`、裸名 |
| 2 | 教案回灌永不触发（score=0） | `indexLessonPlan()` 在 `awaitReview()` **之前**调用，Review 评分异步 15s 后才写入 | `LessonController.java`：`awaitReview()` 提前到 HITL 判断与回灌之前 |
| 3 | 超长 chunk 导致 Milvus 插入失败 | strip HTML 后无空行形成单段 15036 字符，超 Milvus `content` VarChar(8192) 上限 | `DocumentChunkService.java`：单段超长按 `maxSize`(800) 硬切 |

**验证日志**：`[回灌完成] 教案已回灌到知识库: 9 分片, subject=数学, score=94`（修复前 `[回灌跳过] 评分 0 < 70`）。
